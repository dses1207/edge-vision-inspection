# 決策：監看畫面的框怎麼畫

> 定案日期：2026-09-04
> 前置實測：`2026-08-28-sync-verification.md`（時間戳）、`2026-08-28-frame-marker.md`（marker）

## 決策

| 序位 | 方案 | 狀態 |
|---|---|---|
| **第一序列** | **伺服器端燒錄**（nvdsosd 把框畫進畫面後再編碼） | 預設，已上線驗證 |
| **第二序列** | **frame marker**（幀號編碼成方格燒進畫面，前端解碼後疊框） | 已實作可用，備援 |
| 不採用 | 時間戳對齊（含固定偏移校準） | 實測排除，見下 |

切換點：`OVERLAY_MODE=server|client`（`edgevision/api/frontend_api.py`），
前端從 `GET /api/frontend-config` 讀，不需要改前端程式碼。

## 為什麼燒錄排第一

1. **框與畫面天生同幀** —— 框是畫進像素裡的，不存在對齊問題。
2. **前端零工作** —— 給一條 RTSP/WebRTC 就結束。正式 UI 可能不是我們寫的，
   不用交接一套 marker 解碼規格（那套有 5 個實測踩出來的坑）。
3. **任何播放器都能看** —— 手機、大螢幕、舊瀏覽器。

**代價**：前端無法關閉框線（已確認不需要）；每路需要一個 NVENC session。
消費級卡（如 4080）是 8-12 sessions／整台機器，專業卡（如 RTX 6000 Ada）有 3 個 encode engine
且無 session 數上限 —— 這是壓測要分清楚的（測試機的牆 ≠ 架構的牆）。

**燒錄不畫 seg 遮罩**：mask 重建 11ms/台，6 路吃光 15fps 預算，20 路超支 3.3 倍。
遮罩仍算、仍走 WebSocket 給前端當資料。

## 為什麼 marker 是第二序列而不是第一

marker 在技術上更強 —— 它同時給你**精準同步**和**前端可控**（能關框、能畫遮罩）。
排第二純粹是因為它把複雜度推給前端：canvas 取樣、Gray code 解碼、buffer 管理，
而且我們踩過 5 個坑（`imageSmoothingEnabled` 預設 true、H.264 deblocking 污染格子邊緣、
門檻要動態算、ID 繞回時 buffer 不能按數值排序、找不到結果要沿用上一筆）。

**什麼時候該切回 marker**：監看畫面需要遮罩、需要讓使用者開關框線、
或 NVENC 成為確定的瓶頸而「有人看才編碼」做不出來時。

## 為什麼不用時間戳（含舊系統的做法）

我們自己實測排除了四種變體（`2026-08-28-sync-verification.md`）：

| 方案 | 結果 |
|---|---|
| 直接用 rtpTimestamp 配對 | 兩路徑基準不同 |
| 固定偏移校準 | 準確度不足（抖動 200ms） |
| rVFC 的 captureTime | 瀏覽器不給 |
| RTCP SR 自建映射 | 不可行 |
